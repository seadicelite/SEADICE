# Flutterアプリの標準実装

SEADICE の iOS アプリ（Flutter）を新しく作る・改修するときの決まり。`/improve-app` `/release`・新規アプリはこのファイルと [CLAUDE.md](../CLAUDE.md) を読んでから作業する。**コード例・手順・アプリの種類別の規則（通知・投稿・クイズ）は [flutter-howto.md](flutter-howto.md)** にあり、その部品を作るときだけ該当の節を読む。

## 良いアプリの基準（理念から、2026-10-12〜）

作る前・改修の前に、この4つに答えられるかを確かめる。

1. **誰のどんな悩みか**: 「〇〇な人が、△△で困っている」と1文で言える。もとになったメディアの記事・EVIDENCE のトピックがある
2. **使い終わったとき何が変わるか**: Before→After で言える（数字で見られるならなお良い）
3. **AIのチャットでは済まない理由**: 記録して経過を見る・毎日続ける仕組み・その場でできる道具のどれかがある（チャットで1回聞けば済むなら、アプリにしない）
4. **悩みの解決を邪魔するものがない**: 広告なし・登録なし・最初の1回が1タップ。根拠は「もとになった研究」として出典つきで示す

改修のときは、ユーザーの声（フィードバック・不具合報告・レビュー）からどの基準が足りないかを見て直す。

### 目標とのつなぎ（アプリは「悩み → メディア → アプリ」の出口）

規則の本体は [app-publish.md](app-publish.md)（相互送客・もとになった研究）。アプリ側で守ること:

- **メディアへの戻り口は1本**: `https://{メディア}/apps/{appId}/` だけ（個別記事のURLは入れない）。置き場所は、コア機能を終えた直後の小さなテキストリンク（3回目以降に控えめに）と、設定画面の「関連アプリ」の上の「もっと知る（SEADICEのメディア）」
- **根拠の画面**: 「もとになった研究」を出典つきで1画面（記事にある研究・数字だけ。「証明された」と書かない）。研究は複数を、結論・まだわからないこと・出典まで削らずに載せ、1本ずつ折りたたみ、閉じても問いと結論の1文は見せる。機能をメインにし、研究は別のタブに置いて、機能の各所から該当する研究へ飛べるようにする（2026-10-14）
- **データは端末内だけ**: SharedPreferences。アカウント登録・個人情報の収集は入れない

## アプリ開発の流れと役（2026-10-27〜）

目的は「ユーザーが魅力と価値を感じ、課金してでも使いたいアプリ」を、長く運営できる形で作ること。却下の大半は 4.3（似たアプリ・量産）で、アカウント全体の印象で決まる。作る本数を減らし、1本ずつ全部の段階を通す。

**指針**
- **迷ったらユーザーファースト**: 役どうしの意見が割れたら、使う人のためになる方を取る
- **市場の選び方**: ニッチなジャンルで勝負する（2026-11-08）。`market` が狙う検索語で App Store を引き、次のどちらかなら作らない: ①同じ悩みを解くアプリで評価数1,000件以上・公開3年以上の古参が上位にいる（悩みが違うアプリは数えない）②上位10本のうち、同じ悩みで評価数100件以上が5本以上。勝つ違いは真似されにくいもの（確かめた出典・続ける記録・SEADICEの名前）に置く
- **本数**: 新規は月3本まで（市場の選び方を通った案、実装を始めた月で数える）。量産はしない（`/gacha` は2026-11-09に削除）。既存アプリは `ct=seadice` の数字で伸びている数本に集中し、ほかは改修のついでだけ
- **費用は抑える**: 通信なし（端末内で完結）が基本。サーバーや外部APIは課金でまかなえる見込みがあるときだけ使い、予算アラート（Google Cloud「お支払い → 予算とアラート」、Anthropic コンソールの上限）と呼び出し回数の上限を入れてから申請する。目安は1アプリ月1,000円（超えたらユーザーに聞く）。判断は「この形で何年続けられるか」。サーバーを使う既存アプリ（栽エンサー・みんなのラブレター・AIBOU・IJIN など）は、次の改修で business が費用と上限を見直す
- **コストを下げる作り方を毎回出す**: 人気のない投稿は TTL で自動削除、一覧はリアルタイム監視でなく引っぱって更新、読むだけのデータは Hosting の静的 JSON、画像は端末に置き共有は縮小版、手書きは線の点、AI は安いモデル・短い文脈・定型文は端末内、件数・文字数・回数の上限。使い勝手を落とす案は取らない
- **デザイン**: アプリは「誠実だけど気持ちいい」。動き・振動・色・着せ替え・記録がたまる見た目を使ってよい。地の色・アクセント色・文字の大きさ・ボタン・機能の順番は、全アプリ共通でなく**ターゲット票から決める**（下の「ターゲット票」）。着せ替えは決めた地のままアクセント色を選べる形（ライト/ダーク切り替えは入れない）。煽り・盛った数字・押し付けの課金案内は禁止
- **課金の線**: 核の機能（最初の価値）は無料。続けて使う人向けの機能（ウィジェットの追加サイズ・着せ替え・振り返り・保存数など）を課金にする
- **ウィジェットと課金は型を使い回す**: ウィジェットは SwiftUI（WidgetKit）＋ `home_widget`、課金は StoreKit・復元・利用規約とプライバシーのリンク。1本目の形を次から使う

**流れ**（新規アプリ。役は [.claude/agents/](../.claude/agents/)、どれも報告だけで直さない）

| 段階 | 役 | 決め方 |
|---|---|---|
| 1. 企画の関門 | `market`（競合）、`business`（売れるか・費用・保守）、`appstore-review`（4.3） | 全部が通すと言ったら作る。4.3 の見込みが高なら作らない。中なら、ほかのアプリとの違いを1文で言えるまで企画を直してもう一度。意見が割れたらユーザーに聞く |
| 2. 設計 | 最初にメインのClaudeが「ターゲット票」を書き、`neuro` がそこからデザイン仕様を出す。続けて `experience`（最初の価値・ウィジェット・気持ちよさ・課金の置き場所）、`neuro`（新規は必ず。確かさA〜D）、サーバー・ログイン・投稿・課金・外部APIがあれば `security`、ウィジェットを足すなら `widget` | 実装の前にターゲット票・デザイン仕様・画面の流れを決める。neuro の案は experience の設計に取り込む（確かさCは根拠が弱いと承知の上で）。値段は business の案で決める。security は「何が狙われるか・破られたら何が起きるか・どう防ぐか・最悪の被害と費用の上限」を表にし、対策を実装に入れる |
| 3. 実装 | （メインのClaude） | このファイルの決まりと [flutter-howto.md](flutter-howto.md) |
| 4. 動かす | `device-check` | 例外・空の画面・動かないボタンを直してから次へ |
| 5. 確かめる（同時に） | `user`（複数）・`design`、条件つきで `security`・`source-check` | user は人と日数を変えて何人でも（初めての人・3日目で飽きかけた人・1週間空いて戻った人・30日続けている人など）。新規では「初めて開いた人の最初の10秒」を必ず1人、ターゲット票の人を必ず1人。`design` はターゲット票のデザイン仕様とずれていないかも見る。security はサーバー・ログイン・投稿・課金・外部APIがあれば必ず。高が残っている間は申請しない |
| 6. 申請前 | `appstore-review` | 新規・アップデート・再申請のたびに必ず |

- **アップデート**: 6 だけ（ただし見た目・機能を変える改修は、先にターゲット票を書く・見直す）。サーバーや課金を触ったら `security` も。小さな直しでは呼ばない
- **4.3 で却下されたアプリ**: 1 から通し直し、見込みが一番高い1本だけ作り替える
- **却下されたら審査役を育てる**: 却下の理由を `appstore-review` の「何を見るか」に1行足す
- **公開後**: Firestore `feedback` の「要望」「不具合」を週1回読み、不具合はそのアプリの次にやることの先頭へ（読み取りは Firebase コンソールのみ。[improve/apps.md](improve/apps.md) の点検）

### ターゲット票（2026-11-10〜、新規と見た目・機能を変える改修で必ず）

「誰のためか」を決めずに作ると、色も機能も全アプリ同じになり、使う人に合わず 4.3（似たアプリ）にも近づく。設計の最初に、アプリのフォルダに `TARGET.md` を書く。**見た目・機能を変える改修では「誰」「いつ・どこで・どう持つ」「そのときの気持ち」の3項目だけでよい**。わからない所は推測で埋めず「未確認」と書き（未確認の項目はデザインの決め手に使わず既定のままにする）、[docs/problems/](problems/README.md)・もとの記事・`market` の調べから埋める。

| 項目 | 書くこと（例） |
|---|---|
| 誰 | 1文。「〇〇な人が、△△で困っている」（例: 共働きで、夜に子どもの寝かしつけ後に家計を見直したい30代） |
| 年齢・目・指 | 年配・老眼・初めてスマホのアプリを入れる人か、など |
| いつ・どこで・どう持つ | 寝る前の暗い部屋／通勤中に片手／机で落ち着いて／外で日なた |
| そのときの気持ち | 不安・急いでいる・楽しみ・疲れている |
| なじみのある物 | いま使っている紙・アプリ・道具（形と言葉をそれに寄せる） |
| 払う理由 | 何が増えるなら月いくら払うか（`business` の案） |
| 使い終わりの一言 | 使った後に本人が言いたいこと（Before→After） |

`neuro` はこの票から、次の**デザイン仕様**を表で出し、`TARGET.md` の下に書き足す。決め方の表は [neuro.md](neuro.md) の「ターゲットから決める」。

- 地の色（ダーク固定かライト固定か）・アクセント色1つ（ほかの自分のアプリと見分けがつく色）・文字の大きさ・ボタンの大きさと置き場所・アイコンに文字を添えるか・動きと振動
- 核の機能1つと、タブの順番・ウィジェットの種類（いつ・どこでから決める）
- 課金を案内する場面（価値を感じた直後のどこか）
- 画面の大きさごとの形（iPhone の小さい画面・大きい画面・横向き・iPad・Mac）。ターゲットがよく使う端末を先に決め、ほかの大きさでも崩れないこと（下の「文字の大きさとレスポンシブ」）

サイト（seadice.win）は `#00FFD1`／`#05050C` のブランド色のまま。アプリはターゲットに合わせて色を変え、SEADICE とのつながりは名前と設定画面で示す。色は「この色で気持ちが落ち着く・買いたくなる」で選ばない（根拠なし、[neuro.md](neuro.md) の使わない説）。読みやすさ・なじみ・見分けやすさで選ぶ。

## 新規アプリの企画方針（Before→After型ニッチ、2026-08-08〜）

- **「〇〇な自分から△△な自分へ」を1アプリ1テーマで**。「A→B」を一言で言えるか（夜更かし脳→早起きできる自分）を分かりやすさの基準にする
- **狭く具体的な悩みに絞る**（「セルフコンパッション」でなく「仕事のミス直後の自己批判を鎮める」）。名前・コンセプトは本人が検索しそうな平易な言葉にし、学術ジャンル名を前面に出さない
- 既存の `/tools/`・企画メモと重ならないか確かめてから着手する
- **既存アプリのパック・機能追加で済むなら別アプリにしない**（2026-10-13、恋愛の科学が 4.3/4.2.6）。Apple は「同じアカウントの他アプリの課金・機能追加で出せないか」「コードや素材を共有していないか」を問う。EVIDENCE と同じ「研究をカードで読む」形はテーマを変えても別アプリにならず、テーマ別の研究は EVIDENCE のカテゴリかパックとして足す。別アプリにするのは核の機能（記録・道具・練習など）がどの既存アプリとも違うときだけ
- **企画の時点で、同じ仕組みの自分のアプリと、ありふれた分野かを確かめる**（2026-10-14、安心QRが 4.3）: ①同じデータ・リスト・仕組み・**入力の形**を使う自分のアプリ（未申請も含む）がないか（2026-11-04、怪しい人チェックはトークのスクショを読む形が本音診断と同じで 4.3）②App Store に大量にある分野（QRリーダー・電卓・タイマー・メモ・天気など）でないか。その分野なら、違いがあっても単独のアプリにせず既存アプリの機能にする。①②のどちらかに当たれば、作る前にユーザーに「〇〇の機能として足す」案を出す
- **却下されたアプリのプロジェクトを作り替えて別アプリとして出さない**（2026-10-20、4.3(a) で Extended Review の警告）。4.3 の企画は、同じ記録で核の機能を変えて出し直すか、審査を通った既存アプリの機能にするか、止める。新しい Bundle ID で作り直さない。代わりに「サイトのツールで出す・需要を見る」は勧めない（使われず、需要の確かめにも収益にもならない、2026-11-03・11-09 に二度）

## 基本の約束

- **iOS Deployment Target は `15.0`**（2027年春以降 15.0 未満は提出不可、`ITMS-90068`）。`ios/Podfile` の `platform :ios`・`post_install` の `IPHONEOS_DEPLOYMENT_TARGET`、`project.pbxproj` の3か所をそろえる（`flutter create` 直後は 13.0 のことがある）。ipa の前に `grep -n "DEPLOYMENT_TARGET\|platform :ios" ios/Podfile ios/Runner.xcodeproj/project.pbxproj` で全部 15.0 か確かめる（Podfile の `post_install` だけ 14.0 で失敗した例、2026-10-13）
- **シミュレーターで確かめた後の ipa は必ず `flutter clean` してから作る**（2026-11-04）。native assets（`objective_c.framework` など）がシミュレーター用のまま入り `90208`・`91169` になる。作ったら `vtool -show-build build/ios/archive/Runner.xcarchive/Products/Applications/Runner.app/Frameworks/*.framework/* | grep platform` が全部 `IOS` か確かめる。失敗したアップロードでも番号は使われるので、作り直しではビルド番号を上げる
- `Color.withOpacity()` は使わず `withValues(alpha: x)`。`AnimatedBuilder` の未使用引数は `(_, _)`
- 永続化は SharedPreferences。プライバシーポリシーは `p/privacy/{appId}/index.html`（[app-publish.md](app-publish.md)）
- 絵文字は使わない（`Icon(Icons.xxx)`、データ定数に絵文字フィールドを設けない）
- アプリアイコンが未作成なのはアセット待ちで、`/improve-app` の品質評価で減点しない
- 色はターゲット票のデザイン仕様で決める。ダークに決めたときの初期値: 背景 `_bg = Color(0xFF05050C)`、カード `_cardBg = Color(0xFF0C0C1A)`（アクセントは `0xFF00FFD1` を使い回さず、アプリごとに決める）。文字と地は4.5:1以上、アイコンと地は3:1以上

### 地の色は固定（ダークかライトかはターゲット票で決める、2026-11-10〜）

`ThemeData.dark()` か `ThemeData.light()` のどちらかに固定し、`themeMode` を明示する。端末追従・切り替えトグルは作らない。どちらにするかはターゲット票で決める（長い文を読む・昼に使う・年配が多い → ライト、暗い所で短く使う → ダーク。理由は [neuro.md](neuro.md)）。ターゲット票がまだない既存アプリは今の地のまま（ほとんどはダーク、恋愛の科学はライト固定の例外）にし、見た目を変える改修のときに票を書いて決め直す。変えたら [improve/apps.md](improve/apps.md) の変更履歴に1行残す。

### 広告は一切実装しない（2026-07-30〜）

AdMob アカウントが停止したため。`google_mobile_ads`・リワード広告・「広告を見て応援」タイルは入れず、既存アプリに残っていれば改修時に消す。上限に達したときも広告で回数を足す導線は作らない。

### Claude APIを使うアプリの利用回数制限

日次の無料回数だけが API 代の防波堤なので、全アプリ同じ形にする。作り方（プロキシ）は [flutter-howto.md](flutter-howto.md)。

- SharedPreferences に「最終利用日」と「当日のカウント」。日付が変わっていたら0に戻してから判定（手動リセットは作らない）。キー名には `_appId` を含める
- 目安は1日3回（機能の重さで変えてよい）。App Store の説明文と最初の画面にも同じ回数を書く
- **エラー時はフェイルクローズ**（例外が出たら上限扱いでブロック）。改修時にも必ず確かめる
- 上限のメッセージ: 「本日の利用回数の上限に達しました。明日またお試しください」

## Flutterアプリの設定画面の標準構成

新規・改修ともこの並びにそろえる（部品のコードは [flutter-howto.md](flutter-howto.md)）。

1. **アプリを一緒に育てませんか？**（最上部の目立つカード）→ `FeedbackFormPage`（テキストボックス＋送信だけ）。要望・アイデアの募集に絞る
2. **不具合を報告する**（1のすぐ下の別カード）→ `BugReportFormPage`。プレースホルダーは「どんな操作で・どんな不具合が」。送信先は1・2とも seadiceweb の Firestore `feedback` を共用し、2は `source` を `'{appId}-bug'` にする（新しいコレクションは作らない）。1・2は色付き枠・太字・アイコンで3と別の見た目にする
3. **App Storeで評価する**（`in_app_review` の `requestReview()`、App Store へは遷移しない）/ **アプリを共有する**（`share_plus` 11 の新API、`sharePositionOrigin` 必須）/ **お問い合わせ**（`mailto:hi@seadice.win`。1・2は一方通行で返信できないので、返信が要る相談はアプリ内フォームでなくメールで受ける）/ **もっと知る（SEADICEのメディア）** / **関連アプリ** / **SEADICEのホームページ** / **プライバシーポリシー** / **オープンソースライセンス**（`showLicensePage`）/ **バージョン情報**（1つのCardにまとめる）

- **「活動を支援する」は置かない**（2026-09-30〜）。アプリから寄付ページへの誘導は任意でも 3.1.1 で却下される（hiru10）。サポートURLも `https://seadice.win/`。既存アプリにあれば消す。伸びたアプリだけ後から IAP の投げ銭を足す

### 「関連アプリ」

- **`p/released-apps.json` を唯一の正とする**（記憶やテンプレートの使い回しで決めない。ジャンル違いのアプリが貼られたままだった事故あり）
- 同じジャンルの公開済みアプリを2〜3個。なければ released-apps.json から2〜3個（固定の2本を使い回さない）。自分しか載っていなければ欄ごと作らない
- リンクは `appStoreUrl`（App Store 直リンク）。seadice.win 経由にしない
- 審査を通ったアプリは [app-publish.md](app-publish.md) の手順で released-apps.json に足す

## 初回起動は「最初の一歩」（2026-10-27〜、ウェルカムダイアログを置き換え）

最初の10秒で一度「これいい」を体験してもらう（設計は `experience`）。

- **最初の画面そのものが最初の一歩**: 気分を1タップ・心配を1行など、数秒で終わる操作を説明なしで置き、終わったらすぐ結果を見せる
- **説明は画面の中に1行だけ**。アプリの約束（登録なし・記録は端末の中だけ）は小さく1行
- **ダイアログは**どうしても1つ選んでもらうときだけ: 1枚・1〜2行・ボタンはやることを言う（「今日の気分を記録する」）。アプリの地のまま
- **初回に聞かない**: 名前・細かい目標・通知の許可・課金の案内。初期値を入れておく
- 既存アプリのウェルカムダイアログ（白背景・イラスト・「はじめる」・`onboarding_shown`）は改修のついでに置き換える

**後で、一度だけ聞く**（フラグは SharedPreferences: `first_step_done`・`notif_asked`・`widget_hint_shown` など）

| 何を | いつ |
|---|---|
| 通知の許可 | 最初の一歩の直後に「明日もこの時間にお知らせしますか？」→「はい」の後にOSのダイアログ |
| 課金の案内 | 価値を感じた後（何回目かは experience が決める）。断ったら同じ場所でしつこく出さない |
| ウィジェットの案内 | 3回ほど使った後に1回だけ |
| App Store の評価 | コア機能3回目の完了時に1回だけ（不具合報告の直後は避ける） |
| カメラ・写真・位置などの許可 | その機能を使う直前に、目的を1行添えてから |
| 投稿の約束への同意・匿名IDの作成 | 最初に投稿しようとしたとき（読むだけならすぐ見られる。審査 1.2） |

- **安心の説明は隠さない**: 気になる情報を入れる画面では、入力欄のそばに「どこにも送りません（端末の中だけ）」など扱いを1行で
- **アップデート通知は必ず入れる**: 起動時に App Store の最新版を確かめ、古ければ閉じられるダイアログを出す（強制にしない。審査中のビルドや通信不調で使えなくなるのを避けるため）。App Store ID 未定なら飛ばし、通信エラーは握り潰す。最初の一歩の前には出さない（コードは [flutter-howto.md](flutter-howto.md)）

### 離脱しにくい画面（2026-10-27〜）

閉じにくくする仕掛けでなく、待たせない・迷わせない・失わせないことで離れにくくする。

- **すぐ開く**: 起動から最初の画面まで1秒以内。起動時に通信を待たず、前回の中身を先に出して裏で更新する
- **開いたらすぐ核の1画面**: 2回目からは前回の続き。メニューや一覧を経由させない。核の操作は1タップ目で始められる
- **アプリを開かずに始められる**: ウィジェット・クイックアクション（`quick_actions`）・通知から該当の画面へ直接
- **親指で届く**: 毎日押すボタンは下半分、押せる所は44pt以上
- **行き止まりがない**: どの画面にも次にやることが1つ。空の画面には「最初の1件を記録する」ボタン
- **失わない**: 入力は打つそばから保存。消す操作は取り消せる
- **通信がなくても使える**: 核の機能は機内モードでも動く
- **割り込まない**: 使っている途中に全画面の案内（課金・評価・お知らせ）を出さない。出すのは用事が終わった後

## 文字の大きさとレスポンシブ（全アプリ、2026-10-13〜）

- **下から出る読みもの**（showModalBottomSheet）: 本文 `fontSize: 16`・`height: 1.8` 以上、`isScrollControlled: true`・`useSafeArea: true`、中身は `SingleChildScrollView` で高さは画面の85%まで、`constraints: BoxConstraints(maxWidth: 640)`。見本は enneagram の `_showReadingSheet`

## キーボードを閉じられない不具合の防止（全アプリ必須）

- `TextField` を含む全画面の `Scaffold` の `body` を、タップで `FocusScope.of(context).unfocus()` する共通 Widget（`KeyboardDismissOnTap`、[flutter-howto.md](flutter-howto.md)）で包む
- 送信ボタン・`onSubmitted` の先頭でも `unfocus()` を呼ぶ
- `textInputAction` は最後が `done`、途中は `next`。`onSubmitted` で次へ `requestFocus()` か `unfocus()`

## App Storeリリース時の出力ルール

`/release` や App Store Connect 登録の準備では、`APPSTORE_SUBMISSION.md` に書くだけでなく、**同じ内容をチャットにも直接出す**（ユーザーはチャットからコピペする）。出す項目: 基本情報（アプリ名/サブタイトル/Bundle ID/カテゴリ/年齢制限/価格/プライバシーポリシーURL/サポートURL/著作権）・キーワード・プロモーションテキスト・説明文・審査メモ・App Privacy。アプリ名や機能が変わったら、ファイルを直してから出す。公開済みアプリのアップデートは新機能と変わった項目だけ出す。

**App Privacy の取り残しを毎回確かめる**（2026-11-10）: アップデートの提出前に、App Store Connect の「App のプライバシー」が今のコードと合っているかを見る。広告（AdMob）をやめたアプリには「広告データ・デバイスID・おおよその位置情報・トラッキングに使用」が古い申告のまま残りやすく、ATT がないと 5.1.2(i) で却下される（LUCK UNLUCK 8/24、本音診断 11/09）。SEADICE のアプリはトラッキングをしないので、「トラッキングに使用されるデータ」は常に空。manual.md に提出を書くときは、正しい申告の中身を1行で添える。

スクリーンショットと App Store での見え方の確認は [flutter-howto.md](flutter-howto.md) と [mockup.md](mockup.md)。
